# Message rendering and direction

Required when touching message HTML, images, direction or outgoing MIME.

## HTML and resources

- Qt rich text can fetch resources, ignores `display:none`, and can draw stylesheet text. Sanitize before handing HTML to it: tokenize → tree → clean → serialize. Regex tag matching fails on quoted `>` characters. Do not turn this intentionally limited parser into an HTML5 tree builder that rearranges sender content.
- Keep `MAX_TREE_DEPTH`: recursive tree walks run on the shell's GUI thread. Sanitize once per message; derive formatted, reading and fallback plain-text views from that result. Cache sender HTML, not sanitizer output, so fixes apply to cached mail.
- Reading mode builds a fresh tree with text, checked `href`/`src`, and capped numeric image dimensions only. Do not copy sender class/style/color/alignment/background attributes.
- Escape text-node `<` and `>` when serializing: unwrapping and joining nodes can otherwise create new markup. Decode character references in style values before splitting declarations.
- HTML `background` is a resource URL, not a color. Refuse resource attributes before evaluating appearance preferences.
- Hidden-content detection must not treat container `font-size:0`, unclipped `max-height:0`, or `mso-hide:all` as universally hidden. Child font sizes, overflow and Outlook-only semantics matter.
- Reading-mode links allow `mailto:` and public-host HTTP(S). Refused addresses leave their labels visible.
- Never let Qt fetch original remote image URLs. With images enabled, fetch through `scripts/image_fetch.py` and `public_http.py`: checked public DNS, pinned connections, no redirects, size/deadline bounds, and supported raster signatures matching the declared type. Return only successful images as data URIs; omit pending/refused sources. Exclude tracking pixels and hidden images.
- `public.image` shrinks oversized PNG and JPEG bodies (`src/public_http/downscale.rs`) because Qt decodes every embedded image at full size on the GUI thread at each repaint. Anything over 2400 px wide or 6 MP is resized to at most 1600 px wide and about 4 MP, keeping the aspect ratio, camera rotation and PNG transparency (not ICC profiles or APNG animation); everything else, and anything that fails to decode, is returned exactly as fetched. Decoding is one image at a time, off the async threads, and an image is refused (`public_image_refused`) when it declares more than 100 MP or its header prices the decode and resize above 512 MiB (the decoded size, plus the larger of the resize intermediate, 16 bytes a pixel of the source width by the target height, and the decoder's extra buffers, a second full-size buffer for an interlaced PNG or 2 bytes a component and pixel for a progressive JPEG, plus 64 MiB; so wide images are cheap and tall narrow ones are not, and about 42 MP of 16-bit RGBA fits only when it is not tall). The outcome for each body, including a failed decode, is cached by content hash (32 MiB, least recently used evicted first), so reopening a message does not repeat the work.
- Sanitized and reading documents share the same policy: `maxImages` bounds all rendered inline, CID and remote images, and each document admits at most 16 MiB of embedded data URI bytes. Image data does not count toward the separate 120,000-character markup/layout refusal. Refused images never reach Qt.
- `cid:` sources are the message's own parts, not remote resources, and Qt has no `cid:` scheme (it logs `Protocol "cid" is unknown` and draws nothing). At `reader.open`, after the resource passes the reader's size limit, the backend reads each embedded image part whose Content-ID the message's HTML names with a `cid:` reference and whose bytes are in the provider resource (verified for IMAP; resources that carry only part locators resolve nothing); parts nothing names are not decoded. It checks and shrinks each exactly like a fetched image (`public_http::embedded_image`), and keeps at most 8 MiB of them beside the prepared source. The sanitized document, the reading document and the plain-text marker list draw a resolved reference as that data URI under the same `maxImages` and 16 MiB budget; an unresolved one is dropped, falling back to its alt text in reading mode. The map comes only from the prepared message: `reader.render` replaces any `inlineImageData` a caller sends.
- The image viewer (`ImagePopover`) pages through one message's pictures: the body's, then its picture attachments. Reading and Original wrap each prepared picture in an `omarchy-image:N` link numbered in document order (`Html.serialize` with `linkImages`), and `Images.documentImages` lists them with the same walk; a picture already inside a sender's link keeps that link, since anchors do not nest, and is still a page of the viewer. Senders cannot write these links: the sanitizer keeps only HTTP(S) and `mailto:` hrefs. Attachment bytes reach Qt only through `attachment.image` (API 10), which sniffs, shrinks and refuses them exactly like a fetched picture; it reads them from the cached message resource when it carries them (no network), and otherwise the viewer downloads the attachment once and sends the provider's bytes to it. HEIC, TIFF and SVG attachments open in another application through the existing attachment path, as does every attachment with an older backend; bytes the backend refuses show "That image is not a picture this can show", and a download that fails shows "That image could not be downloaded" with Try again. In Plain, a sender's remote picture (a public http(s) address) is fetched only for the marker that was clicked; paging to another remote marker offers Load picture instead of fetching it, and a marker that is not a public address (an unresolved `cid:`, a private host, a local path) is refused without a fetch. An attachment declared larger than 16 MiB is not downloaded for the viewer, and one whose size was not declared but whose download is larger than that is not handed to the backend; either way the viewer says the picture is too large to show here. What the viewer draws is the prepared copy: a PNG or JPEG over 2400 px wide or 6 MP is shrunk to at most 1600 px wide and about 4 MP, for body pictures and attachments alike; Save keeps that copy for a body picture and the original file for an attachment. Qt decodes a format the backend does not shrink (GIF, WebP, BMP) at no more than 4096 px a side.
- Remote images default off. “Always show” grants the standing preference; Settings revokes it. See [security boundaries](SECURITY-BOUNDARIES.md).

## Direction and MIME

- Direction belongs to content, not interface mirroring. Leave Qt's natural paragraph direction and `Text.ElideRight` behavior alone when correct; use `undefined` to restore natural horizontal alignment.
- Ask `Direction.resolveSubject`, not `resolve`, for subjects: Latin reply prefixes otherwise override Arabic/Persian text.
- Qt honors `dir`, not CSS `direction`; `promoteDirection` translates it. Base direction and physical stylesheet sides must agree (`baseDirectionAttribute`) or list markers can disappear. A sender's explicit element direction overrides the base default.
- Outgoing right-to-left plain text gains a minimal HTML alternative: escaped text, preserved line breaks, `dir` on the body, no styling. Keep the unchanged plain part first. Left-to-right mail stays plain; calendar RSVPs keep exactly plain/calendar alternatives.
- `nestedBoundary` prefixes its tag so an inner delimiter cannot begin with the outer boundary and confuse multipart splitting.
- Qt ignores `dir` on table cells and their wrapping divs; retain natural first-strong-character resolution there.
