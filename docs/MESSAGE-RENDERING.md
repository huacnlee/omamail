# Message rendering and direction

Required when touching message HTML, images, direction or outgoing MIME.

## HTML and resources

- The sanitizer runs in Rust (`core/src/message/html/`): tokenize → tree → clean. `reader.open` and `reader.render` hand the app trees, never markup. `src/mail/message/html.ts` serializes those trees into the subset the reader's `TextView` reads, copying only named, re-checked values (text, `mailto:` or public HTTP(S) `href`, `data:` raster `src`, `alt`, numeric sizes). Regex tag matching fails on quoted `>` characters. Do not turn this intentionally limited parser into an HTML5 tree builder that rearranges sender content.
- Keep the depth limits (`MAX_DEPTH` in `core/src/message/html/tree.rs` and in `src/mail/message/html.ts`): both sides walk the tree recursively. Sanitize once per message; derive formatted, reading and fallback plain-text views from that result. Cache sender HTML, not sanitizer output, so fixes apply to cached mail.
- Reading mode (`core/src/message/html/reader.rs`) builds a fresh tree with text, checked `href`/`src`, and capped numeric image dimensions only. Do not copy sender class/style/color/alignment/background attributes.
- Escape text-node `<` and `>` when serializing: unwrapping and joining nodes can otherwise create new markup. Decode character references in style values before splitting declarations.
- HTML `background` is a resource URL, not a color. Refuse resource attributes before evaluating appearance preferences.
- Hidden-content detection must not treat container `font-size:0`, unclipped `max-height:0`, or `mso-hide:all` as universally hidden. Child font sizes, overflow and Outlook-only semantics matter.
- Reading-mode links allow `mailto:` and public-host HTTP(S). Refused addresses leave their labels visible.
- The reader's `TextView` never fetches: `renderImage` in `src/features/reader/Body.tsx` draws a picture only from raster bytes already in the document. Never hand it an original remote image URL. With images enabled, the reader asks `public.image` (`core/src/public_http/`): checked public DNS, pinned connections, no redirects, size/deadline bounds, and supported raster signatures matching the declared type. Only successful images come back, as data URIs; pending and refused sources are left out. Tracking pixels and hidden images are excluded.
- `public.image` shrinks oversized PNG and JPEG bodies (`core/src/public_http/downscale.rs`) so the window never decodes a huge picture at full size. Anything over 2400 px wide or 6 MP is resized to at most 1600 px wide and about 4 MP, keeping the aspect ratio, camera rotation and PNG transparency (not ICC profiles or APNG animation); everything else, and anything that fails to decode, is returned exactly as fetched. Decoding is one image at a time, off the async threads, and an image is refused (`public_image_refused`) when it declares more than 100 MP or its header prices the decode and resize above 512 MiB (the decoded size, plus the larger of the resize intermediate, 16 bytes a pixel of the source width by the target height, and the decoder's extra buffers, a second full-size buffer for an interlaced PNG or 2 bytes a component and pixel for a progressive JPEG, plus 64 MiB; so wide images are cheap and tall narrow ones are not, and about 42 MP of 16-bit RGBA fits only when it is not tall). The outcome for each body, including a failed decode, is cached by content hash (32 MiB, least recently used evicted first), so reopening a message does not repeat the work.
- Sanitized and reading documents share the same policy: `maxImages` bounds all rendered inline, CID and remote images, and each document admits at most 16 MiB of embedded data URI bytes. Image data does not count toward the separate 120,000-character markup/layout refusal. Refused images never reach the window.
- `cid:` sources are the message's own parts, not remote resources, and the reader cannot resolve a `cid:` address itself. At `reader.open`, after the resource passes the reader's size limit, the backend reads each embedded image part whose Content-ID the message's HTML names with a `cid:` reference and whose bytes are in the provider resource (verified for IMAP; resources that carry only part locators resolve nothing); parts nothing names are not decoded. It checks and shrinks each exactly like a fetched image (`public_http::embedded_image`), and keeps at most 8 MiB of them beside the prepared source. The sanitized document, the reading document and the plain-text marker list draw a resolved reference as that data URI under the same `maxImages` and 16 MiB budget; an unresolved one is dropped, falling back to its alt text in reading mode. The map comes only from the prepared message: `reader.render` replaces any `inlineImageData` a caller sends.
- The image viewer (`src/features/reader/ImageViewer.tsx`) pages through one message's pictures: the body's, then its picture attachments (`gallery` in `src/mail/message/images.ts`). Reading and Original wrap each prepared picture in an `omarchy-image:N` link numbered in document order (`toHtml` in `src/mail/message/html.ts`), and `documentImages` in the same file lists them with the same walk; a picture already inside a sender's link keeps that link, since anchors do not nest, and is still a page of the viewer. Senders cannot write these links: the sanitizer keeps only HTTP(S) and `mailto:` hrefs. Attachment bytes reach the window only through `attachment.image`, which sniffs, shrinks and refuses them exactly like a fetched picture; it reads them from the cached message resource when it carries them (no network), and otherwise the viewer downloads the attachment once and sends the provider's bytes to it. Attachments that are not a viewable raster type open in another application through the attachment path; bytes the backend refuses show "That image is not a picture this can show", and a download that fails shows "That image could not be downloaded" with Try again. In Plain, a sender's remote picture (a public http(s) address) is fetched only for the marker that was pressed; paging to another remote marker says the image is on the sender's server and fetches it only after Try again, and a marker that is not a public address (an unresolved `cid:`, a private host, a local path) is refused without a fetch. An attachment declared larger than 16 MiB is not downloaded for the viewer, and one whose size was not declared but whose download is larger than that is not handed to the backend; either way the viewer says the picture is too large to show here. What the viewer draws is the prepared copy: a PNG or JPEG over 2400 px wide or 6 MP is shrunk to at most 1600 px wide and about 4 MP, for body pictures and attachments alike; Save keeps that copy for a body picture and the original file for an attachment.
- Remote images default off. “Always show” grants the standing preference; Settings revokes it. See [security boundaries](SECURITY-BOUNDARIES.md).

## Direction and MIME

- Direction belongs to content, not interface mirroring. Leave the platform's natural paragraph direction and truncation alone when they are correct; use `undefined` to restore natural horizontal alignment.
- Ask `resolveSubject` (`src/mail/message/direction.ts`), not `resolve`, for subjects: Latin reply prefixes otherwise override Arabic/Persian text.
- The sanitizer turns a CSS `direction` of `ltr` or `rtl` into a `dir` attribute when the element has none (`core/src/message/html/mod.rs`). The reader does not use it yet: `toHtml` in `src/mail/message/html.ts` copies no `dir`, so per-element direction is lost. Only the whole body's direction is applied: `bodyDirection` from the backend (resolved by `core/src/message/direction.rs`), set as the `TextView`'s writing direction in `src/features/reader/Body.tsx`.
- Outgoing right-to-left plain text gains a minimal HTML alternative: escaped text, preserved line breaks, `dir` on the body, no styling. Keep the unchanged plain part first. Left-to-right mail stays plain; calendar RSVPs keep exactly plain/calendar alternatives.
- The nested multipart boundary (`nested` in `core/src/message/compose.rs`) gets a prefix its parent cannot start with, so an inner delimiter cannot begin with the outer boundary and confuse multipart splitting.
