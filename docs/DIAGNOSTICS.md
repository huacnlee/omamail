# Error diagnostics

The AI icon beside the status-bar error and on the existing backend setup screen (tooltip: **Diagnose with AI...**), or **Diagnose...** in the AI panel's **More...** menu, opens Omarchy's default external coding agent through `omarchy-agent`. It does not start a mail AI task, resend a failed request or open an internal diagnostic page. The launcher remains available if the mail backend is unavailable.

Backend request failures are batched into `$XDG_STATE_HOME/omamail/diagnostics/errors.json` (default: `~/.local/state/omamail/diagnostics/errors.json`). The log retains at most 100 entries and 64 KiB; consecutive identical failures are recorded at most once per ten seconds. The directory is 0700 and files are 0600. This is a log of backend errors observed by the current UI, not a record of every provider event or failures from before logging was installed.

Each entry contains the time, a known public operation name, a numeric RPC error code and an exact allowlisted error identifier. Unknown text becomes `unknown_error`. Parameters, mail bodies, subjects, addresses, credentials, conversation content and raw process output are not logged. Input travels to the local recorder through stdin. Existing log entries are sanitized again before a report is produced.

Clicking **Diagnose...** writes a private `report.txt` beside the log, adding the plugin version, pinned backend version and API revision, and passes its path to the external agent. Nothing is sent to an AI by recording an error alone. The diagnostic prompt asks for read-only investigation first and explicitly excludes automatic retries, mail actions, settings changes and history removal. The external agent uses the user's normal Omarchy agent configuration and permissions; these instructions are not a sandbox.

An `agent_invalid_state` failure can mean history was written by an incompatible backend. For example, the calendar-event development version wrote `kind: events` tasks that the pinned 0.9.0 backend cannot read. Because listing validates the full store before starting a new task, one such task blocks new requests too. Do not loosen storage validation or delete conversation files to suppress this error. Confirm the producing version and task state first; a user-authorized move of completed incompatible tasks into a private backup outside `assistant/` can restore the older backend while preserving their files.
