# Microsoft 365

Required when touching `src/providers/m365`, its sign-in, its Graph requests or the Graph token that `calendar.request` and `calendar.discover` borrow.

- A work or school mailbox over Microsoft Graph (`https://graph.microsoft.com/v1.0/me`), mail and calendar behind one device-code sign-in that asks only Graph scopes (`Mail.ReadWrite`, `Mail.Send`, `Calendars.ReadWrite`, plus `offline_access`, `openid`, `profile` and `email`). Microsoft refuses one code that names two resources, so mail never goes through IMAP and SMTP here. There is no built-in Application (client) ID: the person registers a public client (device flow allowed, no redirect URI) and `m365.signInBegin` and `m365.signOut` take its GUID as `clientId`, which the account entry keeps.
- The login authority is the domain after the `@` of the address, when it is a plain hostname (Microsoft takes a domain of an organization for its tenant), because a single-tenant registration, the portal's default, signs in only through its own tenant. If Microsoft answers the device-code request or a refresh with a tenant-not-found code (`AADSTS90002`, `AADSTS900023`), that request is made once more at `organizations`, which a multitenant registration answers; the polls of a sign-in stay at the authority that answered its device-code request. Nothing is stored: every refresh derives the authority the same way, and the account entry has no tenant key.
- A sign-in is accepted when the typed address is the id token's `email`, `preferred_username` or `upn` (case-insensitively): a sign-in name can differ from the mail address. If the token names accounts and none is the address, the sign-in is refused as `m365_wrong_account` with the sign-in name Microsoft reported; if it names nobody (or there is none), as `m365_auth_failed`. Either way nothing is kept.
- The Application (client) ID is one spelling everywhere Rust reads it: a GUID in lower case (`auth::m365::client_id`), for the login requests, the keyring item's `client-id` and the refresh lane, so an ID typed in capitals is the same app after the sign-in. The setup page saves it that way too.
- Tokens never leave Rust. The device code lives in the sign-in table, the refresh token in the keyring (kind `m365-refresh-token`, account and client id as attributes), the access token in `auth`'s in-memory cache. Refresh, single-flight, expiry and saving a rotated refresh token run in `auth/credentials/m365.rs`, in the per-mailbox lane Outlook's refresh also uses (`in_outlook_lane`); its scope, consent and authority rules are its own and Outlook's code is untouched. Every login-host request goes through `auth::m365::login` or `login_at`. A change must not give QML a token, put one in an error, a log or an argument, or let a refresh skip the keyring save.
- Hosts are fixed: Graph requests carry the bearer token only to `graph.microsoft.com` and are never redirected, a `@odata.nextLink` is followed only after `graph::next_link` judges it (https, that origin, a messages listing under `/v1.0/me/`) and a page token that carries one is judged before any request. A test build alone can point the clients at a local listener.
- Message ids are the lower-case base32 of Graph's immutable id (`Prefer: IdType="ImmutableId"`, so a move keeps it): one spelling, and a cache file name within 255 bytes.
- Every response, list, string and wait is bounded. Each request has 20 seconds of its own, waits for a slot and a token included (and, after Graph refused a token, the wait for the mailbox's refresh lane to forget it), and a call around several of them 25; a message body is up to 24 MiB and has 60 seconds of its own, so a slow link can finish it. The call, `reader.open`, the RPC frame and the desktop wait a little longer than that for a Microsoft 365 message and stay at 25 and 30 seconds for everything else. A message uploaded whole (a send, a draft) has a second more for every 256 KiB of its base64, up to what its caller waits: 24 seconds from the desktop, whose call must answer inside 30, and 49 from the outbox, which waits a minute for a delivery and the removal of its draft. Four requests per mailbox are in flight at most; a throttled read is repeated twice after `Retry-After` up to five seconds, a write only after a 429 and a send never. A change Graph answered with a 2xx was done: its answer (the whole message) is not read, and is no failure however long it is.
- A batch (`m365.modify`, `m365.trash`, `m365.untrash`, up to 1000 ids) is not dropped at its deadline. Every request in it ends by the call's 25 seconds, none is begun in the last fifth of them, and one already begun is waited for; so when time runs out the answer names what was done in `succeededIds` and what was never begun (with `m365_timeout`) or not confirmed in `failedIds`, and the window restores only those rows. In a combined change (marking read and archiving, say) a message whose first request ran but whose second could not begin before the deadline is reported failed with `m365_timeout` although its first change was applied: the next listing shows it.
- What `mail.act` plans asks Graph only for an action that moves mail (archive, trash), as IMAP's plans do, and refreshes its token without saving a rotated refresh token: a preview writes nothing, the keyring included.
- A send is `sendMail` with the MIME as base64, a Bcc header included. Microsoft documents nothing about Bcc inside the MIME; on one work tenant it was observed that the blind recipient got the message and the other copy had no Bcc header and did not name the blind address. What a failed send proves is `m365_send_not_attempted` (also a deadline that passed before the request was written), `m365_send_rejected` (and `m365_message_too_large`), which the outbox treats as "definitely not sent", or `m365_send_failed`, which it shows as unknown.
- How large a message these two routes take is not known. This provider was written from Microsoft's pages for sending and for creating a message in MIME format without a size limit for the base64 body to rely on, and none has been verified live: the owner's checks go through an RPC frame of at most 1 MiB, so nothing larger has been sent through Graph. Omamail therefore sets no limit of its own below the 16 MiB every provider's message stops at (`message::MAX_MESSAGE`). A 413, or Exchange's `ErrorMessageSizeExceeded` code in an error body, from `sendMail` or the draft `POST` is `m365_message_too_large`: Microsoft refused the message for its size, nothing was sent or saved, and the outbox treats it as definitely not sent. A larger message on a slow link is given a longer clock (above), never a second attempt.
- Drafts live in the mailbox. `m365.saveDraft {accountId, raw, draftId?}` is Microsoft's "create a message in MIME format": `POST /me/messages` with the MIME as base64 `text/plain`, which Graph keeps in Drafts, answered `{saved, warning, id}` (`id` the new draft's immutable id, empty if the answer did not say). With `draftId` the old copy is deleted only after the new one exists, within five more seconds or what is left of the call's 25, and a failure there is a `warning` on a saved draft. A save whose answer was lost after the request was written (the connection, a deadline, a 5xx) is `m365_draft_unconfirmed`: Graph may have made the draft, so the window says it may already be in Drafts, and the save is never repeated. `m365.deleteDraft {accountId, id}` reads the item first (`$select=isDraft,parentFolderId`) and refuses with `m365_not_a_draft`, sending nothing more, anything that is neither a draft nor in Drafts; then `DELETE /me/messages/{id}`. The outbox deletes the draft a sent message came from the same way. Microsoft's page for deleting a message does not say where the message goes; its page for `permanentDelete` says that action puts the item in the Purges folder of the dumpster, out of Outlook's reach. Observed on one work tenant: a draft created from MIME was listed in Drafts and passed the draft check, and a deleted one did not appear in Deleted Items.
- Messages read up to 24 MiB, each parsed with the shared `message::parse_up_to` behind a gate of two.
- Sign-in states are `pending`, `signedIn`, `declined`, `expired` and `failed` with an `error` code. A sign-out that lands while a grant is being saved leaves nothing saved: the save is checked again afterwards and undone. A poll waits for its token request and the keyring save at most 24 seconds (a keyring may be waiting to be unlocked) and then answers `pending` with the warning `m365_exchange_running` while the exchange goes on; the same request answers its outcome for five minutes after. That warning is the poll's own: a token request that failed in transit, its `m365_timeout` included, saved nothing. The window asks the same request again after such an answer or one that never came, and a sign-in that then ends without a mailbox (cancelled, declined, failed) is signed out, since the backend may have saved it. A late answer of a cancelled sign-in is not signed out while a newer one of the same app is under way, signed in, or saved with its check to be asked again: that one writes the same keyring item, which `m365.signOut` would delete, and a sign-out ends the sign-ins under way of the app it names. One of another app (the ID was changed in between) is signed out at once by its own ID, which leaves the newer sign-in alone. Signing out or removing the mailbox names every ID the window asked a sign-in with, so an older one still exchanging its code cannot save a grant afterwards. A sign-out waits for a refresh that holds the sign-in (a keyring waiting to be unlocked) at most 20 seconds and then answers `m365_timeout`, which the window reports as a sign-out that could not be completed.
- A keyring that is locked when a saved sign-in is restored (`auth_keyring_failed`) passes: the check is asked again on the retry schedule and the window says to unlock the keyring, not to sign in again.
- Limits that are not bugs: Unread and Flagged list the Inbox only; and the Graph token the calendar borrows is the mailbox's one sign-in, so it carries the mail permissions as well as `Calendars.ReadWrite`.
