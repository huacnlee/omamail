# Exchange (EWS)

Required when touching `src/providers/exchange/`, its sign-in, search, paging, send outcomes or calendar.

- On-premises Exchange only: Exchange Web Services over HTTPS with NTLMv2 (including the TLS channel binding) or Basic. Microsoft 365 has no password sign-in and is a different provider.
- The endpoint is typed by the user and decides where the password goes: `https://host[:port]/<prefix>/EWS/Exchange.asmx`, no credentials, query or fragment in it, no redirect followed, no proxy read. NTLM sends a response, never the password; Basic is sent only after a 401 that offers it. Once a stream has signed in with NTLM the client keeps NTLM and the UI writes `ntlm` over `auto` in the account entry, so a later stream offered only Basic (another node behind the same name, something in between) is refused with `exchange_auth_scheme_unsupported` before anything secret is sent. Basic is never kept that way: a first sign-in through something that stripped the NTLM offer would otherwise make a one-time downgrade permanent. Changing the server address or the sign-in name puts the method back to `auto`. ALPN offers `http/1.1` only because IIS refuses connection-bound authentication over HTTP/2, and `ews/conn.rs` keeps one stream per account (hyper's single-connection client) because the sign-in and the certificate hash belong to that stream.
- Every request says its `Content-Length`, an empty one included: hyper leaves it off an empty body and IIS then answers `411 Length Required` instead of its 401 challenge, which looks like a server with no usable scheme. `WWW-Authenticate` is read from every header line, and from a comma-joined line, case-insensitively: IIS sends `Negotiate` and `NTLM` as two lines and the CHALLENGE as `NTLM <base64>` on its own.
- NTLM answers a CHALLENGE only if its TargetInfo has a timestamp, and always includes the MIC, `HTTP/<host>` and the `tls-server-end-point` binding (RFC 5929: the hash of the server certificate, MD5 of the `gss_channel_bindings_struct`). Never retry without them. `ews/ntlm.rs` is checked against the MS-NLMP 4.2.4 vectors and, in the tests, against an independent verifier.
- A 401 to credentials this provider sent latches the account (`exchange_unauthorized`, no traffic) until its settings or password change: directories count failed logons. `exchange.invalidate` (sign-out, removal) drops the account's client and the password it holds once the operation using it ends, and a request that read the password before it and is still waiting for the account answers `auth_signed_out` instead of signing in with it; the window sends it as soon as the sign-out begins and again once the keyring has answered the delete (for a request that read the password in between), the second only if no new sign-in to that mailbox has begun meanwhile. A latched refusal survives only as a salted fingerprint of the credentials. A 401 to a request that carried none says only that the stream lost its sign-in: the request goes once more on a stream signed in again, and a second such 401 is `exchange_auth_failed`, which latches nothing. The first request on a stream is the folder lookup that carries the credentials, so a send is never the request that finds a wrong password. Until the server has accepted a client's credentials once, that sign-in starts only while its whole 20-second request still ends by the call's deadline, and is never cut: a cut one may be counted by the directory as a failed logon that the latch never hears of. Once they have been accepted, a stream opened again (a read repeated after a lost stream, one that waited for its turn) signs in with the time that is left, like a read.
- Removing a mailbox waits until the keyring has confirmed its password deleted, as every provider's removal does: `ExchangeAuth.forgetCredential(done)` answers `false` before the backend is up (the keyring is reached through it, so nothing is touched) or when the delete is refused, and the mailbox stays with the reason on its page until Remove account is tried again. A password left by an older build's removal is still deleted before the same address is added again.
- Ids are the lower-case base32 of the `ItemId` bytes: EWS ids are about 150 base64 characters, and the cache names a file after the id under a 255-byte limit. An id changes when the item moves, so mutations report the ids that were asked about and the next listing is the truth.
- Reads open messages up to 24 MiB of MIME (`ews::MAX_MIME`, through `message::parse_up_to`) because servers are commonly set above the shared 16 MiB and a message Outlook opens must open here; sends keep 16 MiB. Full messages are asked ten to a request, and those that do not fit one 36 MiB response together are read one at a time.
- Every `exchange.*` call answers within 25 seconds (`account::TOTAL`), the wait for the account's turn included, because the window gives a backend request 30 and then stops the whole backend. A read is cut at that deadline and gives the account's turn back with it. A write is never cut once written, so it starts only while its whole 20-second request still ends by the deadline: a change waits for the account's turn only while a write could still start after it (a bare `exchange_timeout` otherwise), and a batch stops between requests. An id is reported done only when every step it needed was confirmed; one whose first step ran but whose second could not start in time is in `failedIds` ("not confirmed") with the ids never reached, each for `exchange_timeout`. The answer's `error` is the code of the first failed id in request order, so it can be another (`exchange_message_not_found` for an earlier id that was gone). The window sends at most 100 ids to a change, one request after another, so each request has its own 25 seconds; its writes must still start within the first 5 of them, so that their 20-second requests end inside it. The window ends the batch at a request that fails as a whole, or in which every id failed and the first for a reason other than `exchange_message_not_found`: the next would meet the same thing. A back-off that would end past the deadline is not waited out.
- The 20-second request deadline does not grow with the message: reading or sending a message of many megabytes needs a link fast enough to carry it in that time, and a slower one ends in `exchange_timeout` for a read and an unconfirmed send.
- `UpdateItem` needs the item's current `ChangeKey`: it is read just before, and an item refused as stale is retried once with a fresh key.
- A search sends one `FindItem` per folder (Inbox, Sent, Drafts): a live Exchange 15.2 refuses a `QueryString` over several folders. The rows are merged newest first and each folder continues from its own offset; user text becomes one quoted AQS phrase and never reaches the server raw. Folder listings page by received time, not offset, so trashing from the list never skips rows. A flagged view has no folder count, and a live Exchange 15.2 left its `TotalItemsInView` minutes behind, so a first page that holds the whole view is counted by its rows, and when it does not, its items are counted with an id-only `FindItem` (up to 1000) instead.
- A send is `CreateItem` with `SendAndSaveCopy` and the MIME as written: Exchange honours a `Bcc` header inside `MimeContent` and keeps it out of the delivered copies. The outcome is one of `exchange_send_not_attempted` (nothing was written), `exchange_send_rejected` (the server refused it: a message over its size limit, MIME it cannot take, no folder for the copy or no right to send) or `exchange_send_failed` (unconfirmed); a send is never repeated. The account's turn, a stream and the signed-in folder lookup must be done before the message is written: within 5 seconds for an `exchange.send` from the window, so that the 20-second request ends inside the call's 25, and within 25 for the outbox's (`exchange::send_queued`), which ends inside the outbox's minute.
- A draft is `CreateItem` with `SaveOnly` into Drafts, the MIME as written and `PidTagMessageFlags` set to read and unsent (MS-OXCMSG), without which a message made from MIME is filed as one received. A save whose answer was lost may have been processed: it is `exchange_draft_unconfirmed` (the draft may already be in Drafts) and is not repeated. A save that replaces a draft deletes the old one only after the new one exists, and a failure there is a warning, never a failed save. `exchange.deleteDraft` reads the item first and deletes only one the server places in Drafts (`exchange_message_not_found` otherwise), with `SoftDelete`: recoverable by the server, and no copy in Deleted Items for every save. The outbox removes the draft a sent message was opened from.
- No Archive: EWS has no plain archive folder name, so Archive is withdrawn rather than guessed. Spam is Junk Email, Trash is Deleted Items; roles come from distinguished folder ids, never display names.
- Response XML refuses a DOCTYPE and bounds depth, attributes per element (64) and elements and attributes together (200,000), with quick-xml's quadratic duplicate-attribute check off.
- Row headers are synthesized from server properties, so every value is written by a stranger and is neutralized before the shared reader sees it (`resource.rs`); full messages go through `message::parse`.

## Calendar

- The mailbox's default `calendar` folder is a calendar source of kind `exchange` (`Sources.withExchangeAccounts`, signalled by `Accounts.calendarProvider`), read and written by `exchange.calendarEvents`, `calendarEvent`, `calendarCreate`, `calendarUpdate`, `calendarDelete` and `calendarRespond` over the same client, lease, latch and deadlines as the mail. It never goes through `calendar.request`: that would be a second path to the server with the same password. A saved `readOnly` is never read back for it.
- A range is one `FindItem` over a `CalendarView`, at most 100 days, which the server expands into occurrences with UTC `Start` and `End`. A view has no offset, so the next answer starts at the latest start seen and an item running there comes again and is kept once; an answer with nothing new, 12 answers or 1000 events end the read as `truncated`. A cancelled item is left out.
- Private, Confidential and any sensitivity not known are masked in Rust as "Private" with their time and nothing else, before the answer reaches the cache, the bar or the agent.
- An all-day event is its wall clock's days (`StartWallClock`, `EndWallClock`, midnight in the zone it was made in), as `startDate` and `endDate`; QML makes them midnight of those days on its own clock. Without wall clocks the days are the UTC dates of the instants plus twelve hours, right from UTC-11 to UTC+12. The wall clocks and the reminder are the part of the view a server might refuse: a first answer that is a server error is asked once more without them.
- **Only a plain appointment is written**: a single item of the default calendar, nobody else on it, made by its owner, not cancelled, recurring or private, of a kind the decoder knows (`CalendarItem::lock`). The list says `editable` and `lock` per event; an update or delete reads the default calendar's folder id (by its distinguished name, as the view does) and the item again with its `ParentFolderId` and attendee lists, and refuses with `exchange_calendar_locked` before anything is sent, so an appointment made into a meeting since, or one the login reaches in another folder, is never written.
- **No write of an appointment mails anybody**: `SendMeetingInvitations`, `SendMeetingInvitationsOrCancellations` and `SendMeetingCancellations` are `SendToNone` on every one, a new item names no attendee and no reminder unless asked for one, and a delete moves the item to Deleted Items. The builder tests assert that nothing else can appear. The one request that reaches a person is the answer to an invitation, below.
- **A write names its version and is never repeated.** The change key the screen drew goes out with `NeverOverwrite`; another one is `exchange_calendar_conflict` and is never retried with a fresh key (the mail side's stale-key retry is for flags). `DeleteItem` takes no `ConflictResolution`, so a delete's version check is the read just before it. An update names the title, the place and the time only when the form changed them, so a drag writes the time alone and nothing the screen drew (the placeholder of an empty subject, a trimmed title) is written back. A write takes no `requestToken`, waits for its turn only while its request can still end inside the call, and is not detached. What proves nothing was done keeps its code; any other failure after the request was written is `exchange_calendar_unconfirmed` ("look at your calendar").
- **Time**: a timed event is written as UTC instants with no zone. An all-day event is written as its days, `YYYY-MM-DDT00:00:00`, with the owner's Windows zone as a `TimeZoneContext` (and as `StartTimeZone`/`EndTimeZone` on an update), because the server keeps it as midnight of the zone it was made in. `zone.rs` maps the IANA name of the computer's zone (`TZ`, else the `/etc/localtime` link) for the common zones; an unknown one is not guessed and the event is made in UTC.
- Notes are written when an appointment is made and never after: what the detail shows is text made from a body that may be HTML and may be cut, so an edit that sent it back would replace what was written with what was shown; the editor hides the field for an existing Exchange appointment. Dragging and resizing go through the same update and name no reminder. Meetings with other people, repeating events and other calendars are changed in Outlook.
- **An event's detail is one `GetItem` when it is opened** (`exchange.calendarEvent`, `CalendarView.readExchangeDetail`), laid over the event the list drew (`ExchangeEvents.withDetail`) in the shapes the Google detail draws: the notes asked for as `Text`, and an `HTML` answer not believed but put through `html_to_text`, control characters removed, at most 16 KiB and said to be cut; at most 200 people; a join link only if it is `https` printable ASCII with no user name. A private event is masked in Rust as in the list. An attendee's own answer is "only relevant to a meeting organizer's calendar item", so on an invitation only the owner's line (`MyResponseType`) says anything and the rest are `unknown`, drawn as "Invited"; on the owner's own meeting every guest's answer is shown. The organizer is not named on the owner's own event that nobody else is on, and somebody else's meeting says "Only its organizer can change this meeting." where an appointment says why it is locked. A detail read without the Exchange 2013 properties offers no answer, because an answer's read cannot go without them. Whether the detail is what the list drew is judged by title, place and (timed) time, never by version keys, which a view may give as the series'; one that differs marks the event stale, keeps the version it was drawn from (a write is then a conflict) and reads the range again. The answer buttons name the detail's own key (`answerKey`). The lock is the stricter of the two reads, and an item outside the default calendar folder (the same `GetFolder` and `ParentFolderId` an appointment's write compares) is locked and cannot be answered.
- **An answer to an invitation is the one thing mailed, to its organizer, and it is guarded twice.** `exchange.calendarRespond` reads the item again (outside the default calendar folder it is `exchange_calendar_locked`) and refuses with `exchange_calendar_not_invitation` anything that is not an invitation the owner was sent: every signal must agree and one that says otherwise vetoes (a meeting, a single item or one event of a series and never a master, not private, not cancelled, a `MyResponseType` of an attendee, `IsOrganizer` not true, `AppointmentState` with the received bit when given, `AcceptItem` listed when `ResponseObjects` are). It also reads the Inbox's `MeetingCancellation` messages (class `IPM.Schedule.Meeting.Canceled`, newest hundred, one the server says is out of date (`IsOutOfDate`: the organizer took the owner off and put them back, say) ignored, matched by `UID`, else by the calendar item the message names as its own (`AssociatedCalendarItemId`); one naming an event of a series by `RecurrenceId` is for the item at that place, found by its own `RecurrenceId` or `OriginalStart` whatever its kind, and may be for an event that says neither, which is a doubt: not answered, and said as "An event of this meeting was cancelled; answer it in Outlook.") and refuses an answer to a meeting its organizer cancelled, failing with the lookup's own code when the Inbox cannot be read. An answer never takes the detail's reduced read: if the full one fails it fails with its code. Then the version: a key that is not the caller's is `exchange_calendar_conflict`, never retried. Only then `CreateItem` of an `AcceptItem`, `TentativelyAcceptItem` or `DeclineItem` with `ReferenceItemId` the item and its version, `SendAndSaveCopy` or, for `send: false`, `SaveOnly`; nothing else is written. `send` is required and the UI always says true. The server re-creates the item on an answer, so the reply carries the new id when given, the range is read again and the view reopens the event by its uid and start (`CalendarView.reopenAnswered`). An uncertain outcome is `exchange_calendar_unconfirmed` ("look at your calendar"), never repeated. Yes and Maybe go at once; "No..." is the delete's confirmation ("Decline and remove", the way out focused); none of the answers is offered while another answer, a decline or any other change is on its way; a meeting its organizer cancelled says so ("The organizer cancelled this meeting.") instead of offering the answers, and no longer shows the owner's answer to it, a sent decline with `remove: true` that, for a single meeting the server left on the calendar, finds it by `UID` and start and deletes it with `SendToNone`, a best effort that never fails the decline.
- **Reminders** are the minutes the server holds (`ReminderIsSet`, `ReminderMinutesBeforeStart`, in the view and the detail), raised on the desktop by the Google machinery (`Sources.nativeCalendarFeatures`, `reminders` overrides on each event), keyed by uid and start so the new id of an answer raises nothing twice, none for an invitation the owner declined, a Private event (masked, it has no reminder) or a meeting the server flags cancelled (the list leaves it out; a meeting cancelled only by a message in the Inbox is still listed, so its reminder still comes and the detail still says it); an event that ends as it starts lasts the on-time minute for the ledger. The reminder controller reads a 31-day view every 60 s per Exchange mailbox on the account's lease. A new Exchange source starts with them on; one saved with them off keeps that. A plain appointment can be given a reminder when it is made and have it changed or removed (`reminderMinutes` 0 to 40320, -1 for none on an update); the update names it only when it changes, and an unchanged one sends nothing.
