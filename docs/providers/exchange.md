# Exchange (EWS)

Required when touching `src/providers/exchange/`, its sign-in, search, paging, send outcomes or calendar.

- On-premises Exchange only: Exchange Web Services over HTTPS with NTLMv2 (including the TLS channel binding) or Basic. Microsoft 365 has no password sign-in and is a different provider.
- The endpoint is typed by the user and decides where the password goes: `https://host[:port]/<prefix>/EWS/Exchange.asmx`, no credentials, query or fragment in it, no redirect followed, no proxy read. NTLM sends a response, never the password; Basic is sent only after a 401 that offers it. Once a stream has signed in with NTLM the client keeps NTLM and the UI writes `ntlm` over `auto` in the account entry, so a later stream offered only Basic (another node behind the same name, something in between) is refused with `exchange_auth_scheme_unsupported` before anything secret is sent. Basic is never kept that way: a first sign-in through something that stripped the NTLM offer would otherwise make a one-time downgrade permanent. Changing the server address or the sign-in name puts the method back to `auto`. ALPN offers `http/1.1` only because IIS refuses connection-bound authentication over HTTP/2, and `ews/conn.rs` keeps one stream per account (hyper's single-connection client) because the sign-in and the certificate hash belong to that stream.
- Every request says its `Content-Length`, an empty one included: hyper leaves it off an empty body and IIS then answers `411 Length Required` instead of its 401 challenge, which looks like a server with no usable scheme. `WWW-Authenticate` is read from every header line, and from a comma-joined line, case-insensitively: IIS sends `Negotiate` and `NTLM` as two lines and the CHALLENGE as `NTLM <base64>` on its own.
- NTLM answers a CHALLENGE only if its TargetInfo has a timestamp, and always includes the MIC, `HTTP/<host>` and the `tls-server-end-point` binding (RFC 5929: the hash of the server certificate, MD5 of the `gss_channel_bindings_struct`). Never retry without them. `ews/ntlm.rs` is checked against the MS-NLMP 4.2.4 vectors and, in the tests, against an independent verifier.
- A 401 to credentials this provider sent latches the account (`exchange_unauthorized`, no traffic) until its settings or password change: directories count failed logons. `exchange.invalidate` (sign-out, removal) drops the account's client and the password it holds once the operation using it ends, and a request that read the password before it and is still waiting for the account answers `auth_signed_out` instead of signing in with it; the window sends it as soon as the sign-out begins and again once the keyring has answered the delete (for a request that read the password in between), the second only if no new sign-in to that mailbox has begun meanwhile. A latched refusal survives only as a salted fingerprint of the credentials. A 401 to a request that carried none says only that the stream lost its sign-in: the request goes once more on a stream signed in again, and a second such 401 is `exchange_auth_failed`, which latches nothing. The first request on a stream is the folder lookup that carries the credentials, so a send is never the request that finds a wrong password. Until the server has accepted a client's credentials once, that sign-in starts only while its whole 20-second request still ends by the call's deadline, and is never cut: a cut one may be counted by the directory as a failed logon that the latch never hears of. Once they have been accepted, a stream opened again (a read repeated after a lost stream, one that waited for its turn) signs in with the time that is left, like a read.
- Ids are the lower-case base32 of the `ItemId` bytes: EWS ids are about 150 base64 characters, and the cache names a file after the id under a 255-byte limit. An id changes when the item moves, so mutations report the ids that were asked about and the next listing is the truth.
- Reads open messages up to 24 MiB of MIME (`ews::MAX_MIME`, through `message::parse_up_to`) because servers are commonly set above the shared 16 MiB and a message Outlook opens must open here; sends keep 16 MiB. Full messages are asked ten to a request, and those that do not fit one 36 MiB response together are read one at a time.
- Every `exchange.*` call answers within 25 seconds (`account::TOTAL`), the wait for the account's turn included, because the window gives a backend request 30 and then stops the whole backend. A read is cut at that deadline and gives the account's turn back with it. A write is never cut once written, so it starts only while its whole 20-second request still ends by the deadline: a change waits for the account's turn only while a write could still start after it (a bare `exchange_timeout` otherwise), and a batch stops between requests. An id is reported done only when every step it needed was confirmed; one whose first step ran but whose second could not start in time is in `failedIds` ("not confirmed") with the ids never reached, each for `exchange_timeout`. The answer's `error` is the code of the first failed id in request order, so it can be another (`exchange_message_not_found` for an earlier id that was gone). The window sends at most 100 ids to a change, one request after another, so each request has its own 25 seconds; its writes must still start within the first 5 of them, so that their 20-second requests end inside it. The window ends the batch at a request that fails as a whole, or in which every id failed and the first for a reason other than `exchange_message_not_found`: the next would meet the same thing. A back-off that would end past the deadline is not waited out.
- The 20-second request deadline does not grow with the message: reading or sending a message of many megabytes needs a link fast enough to carry it in that time, and a slower one ends in `exchange_timeout` for a read and an unconfirmed send.
- `UpdateItem` needs the item's current `ChangeKey`: it is read just before, and an item refused as stale is retried once with a fresh key.
- A search sends one `FindItem` per folder (Inbox, Sent, Drafts): a live Exchange 15.2 refuses a `QueryString` over several folders. The rows are merged newest first and each folder continues from its own offset; user text becomes one quoted AQS phrase and never reaches the server raw. Folder listings page by received time, not offset, so trashing from the list never skips rows. A flagged view has no folder count, and a live Exchange 15.2 left its `TotalItemsInView` minutes behind, so a first page that holds the whole view is counted by its rows, and when it does not, its items are counted with an id-only `FindItem` (up to 1000) instead.
- A send is `CreateItem` with `SendAndSaveCopy` and the MIME as written: Exchange honours a `Bcc` header inside `MimeContent` and keeps it out of the delivered copies. The outcome is one of `exchange_send_not_attempted` (nothing was written), `exchange_send_rejected` (the server refused it: a message over its size limit, MIME it cannot take, no folder for the copy or no right to send) or `exchange_send_failed` (unconfirmed); a send is never repeated. The account's turn, a stream and the signed-in folder lookup must be done before the message is written: within 5 seconds for an `exchange.send` from the window, so that the 20-second request ends inside the call's 25, and within 25 for the outbox's (`exchange::send_queued`), which ends inside the outbox's minute.
- A draft is `CreateItem` with `SaveOnly` into Drafts, the MIME as written and `PidTagMessageFlags` set to read and unsent (MS-OXCMSG), without which a message made from MIME is filed as one received. A save whose answer was lost may have been processed: it is `exchange_draft_unconfirmed` (the draft may already be in Drafts) and is not repeated. A save that replaces a draft deletes the old one only after the new one exists, and a failure there is a warning, never a failed save. `exchange.deleteDraft` reads the item first and deletes only one the server places in Drafts (`exchange_message_not_found` otherwise), with `SoftDelete`: recoverable by the server, and no copy in Deleted Items for every save. The outbox removes the draft a sent message was opened from.
- No Archive: EWS has no plain archive folder name, so Archive is withdrawn rather than guessed. Spam is Junk Email, Trash is Deleted Items; roles come from distinguished folder ids, never display names.
- Response XML refuses a DOCTYPE and bounds depth, attributes per element (64) and elements and attributes together (200,000), with quick-xml's quadratic duplicate-attribute check off.
- Row headers are synthesized from server properties, so every value is written by a stranger and is neutralized before the shared reader sees it (`resource.rs`); full messages go through `message::parse`.

## Calendar

- The mailbox's default `calendar` folder is a calendar source of kind `exchange` (`Sources.withExchangeAccounts`, signalled by `Accounts.calendarProvider`), read and written by `exchange.calendarEvents`, `calendarEvent`, `calendarCreate`, `calendarUpdate`, `calendarDelete` and `calendarRespond` over the same client, lease, latch and deadlines as the mail. Its other calendars, and those other mailboxes share with it, are sources of their own (below). It never goes through `calendar.request`: that would be a second path to the server with the same password. A saved `readOnly` is never read back for it.
- A range is one `FindItem` over a `CalendarView`, at most 100 days, which the server expands into occurrences with UTC `Start` and `End`. A view has no offset, so the next answer starts at the latest start seen and an item running there comes again and is kept once; an answer with nothing new, 12 answers or 1000 events end the read as `truncated`. A cancelled item is left out.
- Private, Confidential and any sensitivity not known are masked in Rust as "Private" with their time and nothing else, before the answer reaches the cache, the bar or the agent.
- An all-day event is its wall clock's days (`StartWallClock`, `EndWallClock`, midnight in the zone it was made in), as `startDate` and `endDate`; QML makes them midnight of those days on its own clock. Without wall clocks the days are the UTC dates of the instants plus twelve hours, right from UTC-11 to UTC+12. The wall clocks and the reminder are the part of the view a server might refuse: a first answer that is a server error is asked once more without them.
- **Only a plain appointment is written**: a single item of the calendar named, nobody else on it, made by its owner, not cancelled, recurring or private, of a kind the decoder knows (`CalendarItem::lock`). The list says `editable` and `lock` per event; an update or delete reads the folder id of the calendar named (the default one by its distinguished name, as the view does) and the item again with its `ParentFolderId` and attendee lists, and refuses with `exchange_calendar_locked` before anything is sent, so an appointment made into a meeting since, or one the login reaches in another folder than the one named, is never written. A meeting the owner organises is listed `editable` as a meeting (`meeting` true, `CalendarItem::meeting_lock`: a single meeting they sent with no room on it), which these writes still refuse: it is the meeting calls'.
- **No write of an appointment mails anybody**: `SendMeetingInvitations`, `SendMeetingInvitationsOrCancellations` and `SendMeetingCancellations` are `SendToNone` on every one, a new item names no attendee and no reminder unless asked for one, and a delete moves the item to Deleted Items. The builder tests assert that nothing else can appear. The one request that reaches a person is the answer to an invitation, below.
- **A write names its version and is never repeated.** The change key the screen drew goes out with `NeverOverwrite`; another one is `exchange_calendar_conflict` and is never retried with a fresh key (the mail side's stale-key retry is for flags). `DeleteItem` takes no `ConflictResolution`, so a delete's version check is the read just before it. An update names the title, the place and the time only when the form changed them, so a drag writes the time alone and nothing the screen drew (the placeholder of an empty subject, a trimmed title) is written back. A write takes no `requestToken`, waits for its turn only while its request can still end inside the call, and is not detached. What proves nothing was done keeps its code; any other failure after the request was written is `exchange_calendar_unconfirmed` ("look at your calendar").
- **Time**: a timed event is written as UTC instants with no zone. An all-day event is written as its days, `YYYY-MM-DDT00:00:00`, with the owner's Windows zone as a `TimeZoneContext` (and as `StartTimeZone`/`EndTimeZone` on an update), because the server keeps it as midnight of the zone it was made in. `zone.rs` maps the IANA name of the computer's zone (`TZ`, else the `/etc/localtime` link) for the common zones; an unknown one is not guessed and the event is made in UTC.
- Notes are written when an appointment is made and never after: what the detail shows is text made from a body that may be HTML and may be cut, so an edit that sent it back would replace what was written with what was shown; the editor hides the field for an existing Exchange appointment. Dragging and resizing go through the same update and name no reminder.
- **An event's detail is one `GetItem` when it is opened** (`exchange.calendarEvent`, `CalendarView.readExchangeDetail`), laid over the event the list drew (`ExchangeEvents.withDetail`) in the shapes the Google detail draws: the notes asked for as `Text`, and an `HTML` answer not believed but put through `html_to_text`, control characters removed, at most 16 KiB and said to be cut; at most 200 people; a join link only if it is `https` printable ASCII with no user name. A private event is masked in Rust as in the list. An attendee's own answer is "only relevant to a meeting organizer's calendar item", so on an invitation only the owner's line (`MyResponseType`) says anything and the rest are `unknown`, drawn as "Invited"; on the owner's own meeting every guest's answer is shown. The organizer is not named on the owner's own event that nobody else is on, and somebody else's meeting says "Only its organizer can change this meeting." where an appointment says why it is locked. A detail read without the Exchange 2013 properties offers no answer, because an answer's read cannot go without them. Whether the detail is what the list drew is judged by title, place and (timed) time, never by version keys, which a view may give as the series'; one that differs marks the event stale, keeps the version it was drawn from (a write is then a conflict) and reads the range again. The answer buttons name the detail's own key (`answerKey`). The lock is the stricter of the two reads, and an item outside the default calendar folder (the same `GetFolder` and `ParentFolderId` an appointment's write compares) is locked and cannot be answered.
- **An answer to an invitation is the one thing mailed, to its organizer, and it is guarded twice.** `exchange.calendarRespond` reads the item again (outside the default calendar folder it is `exchange_calendar_locked`) and refuses with `exchange_calendar_not_invitation` anything that is not an invitation the owner was sent: every signal must agree and one that says otherwise vetoes (a meeting, a single item or one event of a series and never a master, not private, not cancelled, a `MyResponseType` of an attendee, `IsOrganizer` not true, `AppointmentState` with the received bit when given, `AcceptItem` listed when `ResponseObjects` are). It also reads the Inbox's `MeetingCancellation` messages (class `IPM.Schedule.Meeting.Canceled`, newest hundred, one the server says is out of date (`IsOutOfDate`: the organizer took the owner off and put them back, say) ignored, matched by `UID`, else by the calendar item the message names as its own (`AssociatedCalendarItemId`); one naming an event of a series by `RecurrenceId` is for the item at that place, found by its own `RecurrenceId` or `OriginalStart` whatever its kind, and may be for an event that says neither, which is a doubt: not answered, and said as "An event of this meeting was cancelled; answer it in Outlook.") and refuses an answer to a meeting its organizer cancelled, failing with the lookup's own code when the Inbox cannot be read. An answer never takes the detail's reduced read: if the full one fails it fails with its code. Then the version: a key that is not the caller's is `exchange_calendar_conflict`, never retried. Only then `CreateItem` of an `AcceptItem`, `TentativelyAcceptItem` or `DeclineItem` with `ReferenceItemId` the item and its version, `SendAndSaveCopy` or, for `send: false`, `SaveOnly`; nothing else is written. `send` is required and the UI always says true. The server re-creates the item on an answer, so the reply carries the new id when given, the range is read again and the view reopens the event by its uid and start (`CalendarView.reopenAnswered`). An uncertain outcome is `exchange_calendar_unconfirmed` ("look at your calendar"), never repeated. Yes and Maybe go at once; "No..." is the delete's confirmation ("Decline and remove", the way out focused); none of the answers is offered while another answer, a decline or any other change is on its way; a meeting its organizer cancelled says so ("The organizer cancelled this meeting.") instead of offering the answers, and no longer shows the owner's answer to it, a sent decline with `remove: true` that, for a single meeting the server left on the calendar, finds it by `UID` and start and deletes it with `SendToNone`, a best effort that never fails the decline.
- **A meeting with other people is four calls of its own, and the three that mail a person who did not ask refuse unless told, in so many words, that people will be mailed.** `exchange.meetingCreate`, `meetingUpdate` and `meetingCancel` require `sendInvitations`, `sendUpdates` and `sendCancellations` as the boolean `true` (absent, `false`, `"true"` and `1` are `invalid_params`), judged before the account is resolved, the keyring read or a socket opened; the appointment calls keep `SendToNone` and refuse anything with a person on it, so they cannot stand in. The options are Microsoft's: `CreateItem SendMeetingInvitations="SendToAllAndSaveCopy"` with the people as `RequiredAttendees` and `OptionalAttendees`, `UpdateItem SendMeetingInvitationsOrCancellations="SendToAllAndSaveCopy"` with `NeverOverwrite` and a changed list set whole (`SetItemField`) or emptied (`DeleteItemField`), and a cancellation as `CreateItem MessageDisposition="SendAndSaveCopy"` of a `CancelCalendarItem` naming the meeting and its version, with an optional note of at most 2000 bytes, never a bare `DeleteItem`. The people are addresses to be mailed, checked in `guests.rs` by the handler and again by every builder: one `@`, printable ASCII, a dotted domain, at most 254 bytes, at most 200 in all, none twice in either list or another case, not the mailbox's own, and a meeting needs one; a pasted "Ada <ada@example.org>" is refused, never repaired. Meetings are the default calendar's alone.
- **Only a meeting the owner organises, read again and found whole, is changed or cancelled.** `EventDetail::organised` decides on a fresh full read (never the reduced one): in the default calendar folder, a single meeting the owner sent (`MyResponseType` Organizer, `IsOrganizer` not false, `AppointmentState` without the received bit, `CancelCalendarItem` among the response objects when they are listed), somebody on it besides the owner, every person read with an address (a change or a cancellation mails them all, and the question must name them), no room or equipment, not private or cancelled; every signal must agree and one that says otherwise vetoes, else `exchange_calendar_locked` with nothing sent. The detail says why with its own lock: `room` ("A meeting with a room: change it in Outlook"), `guests` ("Not every guest's address could be read: change it in Outlook"), or `meeting`. Any change except one of the owner's own reminder alone mails every guest; that one goes with `SendToNone`, as Outlook sends nothing for it, and answers `sent: false`. A change compares each named list with what the server holds by address, ignoring case: an unchanged list is not written, a change that changes nothing sends nothing (`sent: false`), the owner the server lists on their own meeting is carried over, a list with somebody on it whose address the server did not give is not written (`exchange_calendar_locked`), and a meeting left with nobody is refused. Anybody taken off a list is sent a cancellation by the server. A stale key is `exchange_calendar_conflict`, never retried; an uncertain outcome is `exchange_calendar_unconfirmed` ("the guests may have been told"), never repeated.
- **A cancelled meeting is taken off an attendee's calendar by processing the cancellation, and nobody is mailed.** `exchange.meetingRemove` reads the item again and the Inbox's `MeetingCancellation` messages (only one that is certainly this meeting's: a doubt about an event of a series removes nothing) and takes a single meeting off only when its organizer cancelled it or the owner declined it; anything else is `exchange_calendar_not_removable`, because deleting an unanswered invitation leaves its organizer waiting. A cancellation the server says is out of date (`IsOutOfDate`: the organizer took the owner off and put them back) cancels nothing and removes nothing. A cancellation is processed with `CreateItem MessageDisposition="SaveOnly"` of a `RemoveItem` naming the message, and a refusal of it is said: the calendar item is never deleted instead, which could take off a meeting the server knows is still on. Only a meeting the server itself flags cancelled, and one the owner declined, are moved to Deleted Items with `SendToNone` ("a calendar item is deleted without sending a cancellation message"). The detail says `cancelled` and `canRemove`; the list does not look in the Inbox, so a cancelled meeting is drawn until it is opened and removed.
- **The screen asks before anything reaches people, and the controller refuses a send that was not asked about.** The composer has a guest field for a new Exchange event and for a meeting the owner organises (an appointment stays one), and saving one that reaches people opens the question `ExchangeEvents.reachRequest` builds: the sentence that names the count and the first three addresses ("This sends an invitation to 2 people: ...", "This tells 2 people the meeting changed: .... It tells ... they were removed."), a button that says it again and the way out ("Keep editing") focused. What the write would refuse (an address that is not one, the owner's own, a meeting left with nobody, a repeat the server cannot be told) is said first and asks nothing, and a change of the owner's reminder alone asks nothing. Only then is `confirmedSend` set, which `CalendarController.createEvent` and `updateEvent` require for anything that mails, and the delete question's answer is what `deleteEvent` requires to cancel a meeting. What deleting is (`ExchangeEvents.deleteKind`: an appointment, a meeting cancelled for everybody, an invitation declined, a cancelled or declined meeting removed) decides the question's words, the button's label and the call; a meeting whose people were not read is neither changed nor cancelled. A drag of a meeting the owner organises never writes: it reads the detail and opens the editor over it, and one that changed since it was drawn is not moved.
- **A repeating event is made in the owner's zone, named twice, with its instants still UTC.** `recurrence` on `calendarCreate` or `meetingCreate` (`recurrence.rs`) is a daily, weekly (on chosen days), monthly or yearly (by date or by weekday) rule ending never, on a day or after a count, held to every bound Microsoft's pages give (1 to 999 days or 1 to 99 weeks or months, no interval for a year, so "every second year" is refused; a day of the month 1 to 31; 1 to 999 events; an end no later than 4500) and to its first event: the first day is the event's own for whole days and the caller's local day (`firstDate`) for an instant, must be one of the rule's days (a weekly series whose start is not its first occurrence loses its zone), and an event may not outlast the shortest gap of its rule. The server expands a series on the wall of the zone it was made in, so `Start` and `End` stay UTC instants with their `Z` and the zone is the request's `TimeZoneContext` and the item's `StartTimeZone` and `EndTimeZone` (Table 2's creation zone), the `Recurrence` after the attendee lists, its dates bare. A computer whose zone `zone.rs` does not list makes no series (`exchange_calendar_zone_unknown`), because one made in UTC would move an hour when the clocks change; a single event is unaffected.
- **An event of a series is changed, deleted, cancelled, answered and removed through a scope, never without one.** `scope` is `occurrence` (this event, by its own id; an update makes it an exception) or `series` (the master, read through the event by `RecurringMasterItemId` and written by its own id, at the master's version, which Microsoft says every event shares). A member of a series is `editable` in a range by the rule of its own kind (`CalendarItem::series_lock`, `meeting_lock(true)`), and named with no scope it is `exchange_calendar_locked` (`meetingRemove` too: `occurrence` takes that event off alone; `calendarRespond` with no scope answers the event it names, which Microsoft says answers that occurrence alone); an item that is not the kind the scope says is `exchange_calendar_conflict`, and so is a stale key, never retried. Every event's time of day is `startClock` and `durationMinutes`, put on the master's first day in the zone it says it recurs in (`StartTimeZone`, written as a clock time with that zone, never an instant), refused where the master says neither, refused as `exchange_calendar_zone_differs` where that zone is not this computer's (a time typed on this clock is another time on that wall) and as `invalid_params` where it outlasts the shortest gap of the master's rule; the detail says `timeEditable` where it may change, and the editor otherwise keeps the time fields shut and says why. One event takes instants and no people (they are the series'). **All of a meeting tells the master's people, and only the ones its question named:** `meetingUpdate` and `meetingCancel` with `scope` `series` require `seriesAttendees`, the people the question named (refused without it, and with any other scope), and the client compares them with the master's people on its fresh read (the owner and rooms aside, ignoring case), refusing as `exchange_calendar_conflict`, with nothing sent, when they differ: an exception's own list is not the series'. The detail gives the master's people (`series.attendees`, `attendeesCut`), the question, the guest field for all events and the write start from them, and all of it is locked, saying why, where they were not all read. **A series with an event of its own guests is changed and cancelled one event at a time:** Microsoft does not say what a write to the master mails to somebody added to one event alone, so the master's read asks for its `ModifiedOccurrences`, the people on those exceptions are read in one `GetItem` (at most 50; more, an exception listed with no id, or a failed read lock rather than guess), and any whose addresses are not the master's (the owner and rooms left out, case ignored; a new time or place does not count) make the series' lock `exceptionGuests`; the same check on the fresh read refuses `meetingUpdate` and `meetingCancel` with `scope` `series` as `exchange_calendar_locked`, nothing sent. All of a series is answered through its master (`calendarRespond` `scope` `series`; only a cancellation of the whole series stops it), and a decline of all of it that asks to be removed looks for the master by its own id and by the id the answer gave it, whatever became of any one event, deletes with `SendToNone` a master of the same `UID` the owner declined, and says removed only when neither read finds anything else on the calendar. The detail says what the series is (`series`: the rule in bounded words, else "Repeats" and its kind; the master's version; whether all of it may be changed or answered, judged on the master), and the screens offer "all events" only where it says so. Dragging an event of a series opens the editor and writes nothing. A cancellation names an event by `RecurrenceId`, and one event of a series is taken off by the cancellation that names it, else by deleting it alone; a cancellation of the whole series is the series' removal. Not done: changing how a series repeats after it is made, "this and following", and turning a single event into a series.
- **A cancelled series is removed whole by one call.** `exchange.meetingRemove` with `scope` `series` (`Client::remove_series`) reads the master through the named event, searches the Inbox for cancellations of its `UID` and nothing else (`Cancellation::is_for_series`), and decides before any write (`EventDetail::series_removal`) that the owner was sent the series and its organizer cancelled all of it (the server flags the master, or a cancellation names no event) or at least two of its events one by one; one cancelled event is that event's removal. Each cancellation is processed with the saved `RemoveItem`, the whole series' first, at most 50 in a call (`more` when some are left or no time is left to write another); a refusal of one is said, and nothing is deleted instead (as for a single meeting); a series cancelled as a whole whose cancellation was processed, or that the server flags cancelled, is read again by its master's id and, where the server left it as a meeting the owner was sent, deleted with `DeleteItem` `MoveToDeletedItems` `SendToNone` at the version it has now. Once anything was taken off, a later failure is not the answer: the call says what it did (`count`) and that it did not finish (`more`, or `seriesLeft` where the master is still there because it could not be read again, is not one the owner was sent, or would not go), so the person looks before asking again. A series of which only some events were cancelled is never deleted by its master. The detail says `canRemoveSeries` and `cancelledEvents` (0 for the whole series) from the reads it already makes, and the removal question offers all of it only there. Nobody is mailed.
- **Reminders** are the minutes the server holds (`ReminderIsSet`, `ReminderMinutesBeforeStart`, in the view and the detail), raised on the desktop by the Google machinery (`Sources.nativeCalendarFeatures`, `reminders` overrides on each event), keyed by uid and start so the new id of an answer raises nothing twice, none for an invitation the owner declined, a Private event (masked, it has no reminder) or a meeting the server flags cancelled (the list leaves it out; a meeting cancelled only by a message in the Inbox is still listed, so its reminder still comes and the detail still says it); an event that ends as it starts lasts the on-time minute for the ledger. The reminder controller reads a 31-day view every 60 s per Exchange mailbox on the account's lease. A new Exchange source starts with them on; one saved with them off keeps that. A plain appointment can be given a reminder when it is made and have it changed or removed (`reminderMinutes` 0 to 40320, -1 for none on an update); the update names it only when it changes, and an unchanged one sends nothing.
- **More calendars are found only by requests Microsoft documents, and never by Autodiscover.** `exchange.calendars` (`ews/client/folders.rs`) is a `GetFolder` of the default `calendar` (which must succeed) and a deep `FindFolder` from `msgfolderroot` restricted to the folder class `IPF.Appointment`; a deep traversal searches "all child folders of the identified parent folder", the default calendar's included, so no second search starts there. A server that refuses the restriction is asked again without it, up to five pages, and the whole class is then compared, so `IPF.Appointment.Birthday` is no calendar. The same search below `deleteditems` names the calendars in Deleted Items, which are left out. The folder step is one discovery can do without: when either search fails its code is `steps.folders.code`, and `truncated` says that calendars were left out (more than 100, or pages not read). The window then keeps every calendar of the mailbox found before instead of taking a partial list for the whole, says so in Settings, and drops a calendar only when a discovery that looked for it completely does not list it (`Sources.exchangeLookedFor`). A refused login ends the call. A calendar another person shares is **added by the address of its mailbox** (`exchange.calendarShared`) and read before it is saved: one code for every way of not being shared (`exchange_calendar_not_shared`), a folder whose class is not exactly `IPF.Appointment` included, and another for an address that opens the owner's own default calendar, an alias (`exchange_calendar_own_mailbox`). It is the owner's: discovery never makes it a discovered calendar or drops it, and it is removed only by hand. Not done: the sharing invitations in the Inbox (`IPM.Sharing`, [MS-OXSHARE]) are not read, because the properties that say which folder an invitation is for have not been checked against a real invitation; the shortcuts Outlook keeps for other people's calendars are folder-associated messages ([MS-OXOCFG]) that `FindItem`'s documented traversals do not reach; auto-mapped mailboxes are an Autodiscover answer, which this client never asks; public folder calendars.
- **A calendar is named by an opaque reference, and what may be done in it is decided in Rust from the server's own rights, asked each time.** The `calendar` member of every calendar call (`folders.rs`) is `<folder>` or `<folder>:<address>`: the folder id spelled as a message id, and the other mailbox's primary address in lower case, never the mailbox's own. It is canonical or `invalid_params`, and absent for the default calendar, so every old call and saved file keeps its meaning; a source is kept by the account's id for the default calendar and by a digest of the account and the reference for any other. Another calendar is read by its folder after a `GetFolder` for its class and `EffectiveRights` (`Client::home`): a folder whose class is not exactly `IPF.Appointment` is no calendar (`exchange_folder_unavailable`, as is one that is gone), a range is read only where the user may read (`exchange_access_denied` otherwise), and an appointment is made there only with the right to read and create. Each of its items is judged by its own `item:EffectiveRights`, asked in the `CalendarView` of every calendar but the default one and again on the read before a write (an answer that names none grants none): an Editor's share lets every item be changed, an Author's only the user's own, a Reviewer's none, and an item without the right to modify is locked (`Lock::Calendar`). **Nothing is deleted in another mailbox's calendar**: a delete moves the item to Deleted Items, and which mailbox's Deleted Items that is for a calendar of another mailbox is not something Microsoft's pages say and has not been checked, so `calendarDelete` naming one is `exchange_calendar_locked` before the account is looked up, and the screen offers no delete there and says why; in the owner's own other calendars an item is deleted by its own rights. An item read from any folder but the one named is locked, and all of a series is never written outside the default calendar: one event at a time. **Meetings, answers to invitations and removals are the default calendar's alone**: a call naming another is `exchange_calendar_locked` after the request is judged and before the account is looked up (`folders::default_only`), a meeting there is locked whoever organises it (`CalendarItem::other_lock`), and its detail is the item alone, with no answer, removal or series. In another mailbox Microsoft says a user with folder permissions and not delegate access "might be able to create items in the folders, but they cannot send the items", and the cancellations and invitations these calls are judged on are looked for in the owner's own Inbox, which says nothing of another calendar's meetings. Private and Confidential items are masked there as in the default calendar. On the screen each calendar is a source (`Sources.applyDiscovery`, `Sources.addShared`) with its own colour and switch: another mailbox's calendar is named with whose it is, one added by hand survives discovery and is the only one removed by hand, reminders start off for every calendar but the default one, the composer's picker offers only calendars the rights let the owner write to, and the guest field is shown only for the default calendar.
